## 1. 全体方針

### 1.1 構成

```
ブラウザ（React）  ──HTTP（JSON）──▶  Spring Boot（REST API）  ──▶  MySQL
                   ◀─────────────
```

- React は画面の表示と画面遷移を担当し、データの取得・保存は REST API を呼び出して行う。
- API のURLはすべて `/api` から始める。
- リクエスト・レスポンスの本文は JSON とする（JSONのキー名は camelCase）。

### 1.2 認証方式：セッション方式

- ログインに成功すると、サーバーがセッションを作成し、セッションIDを Cookie（`JSESSIONID`）でブラウザに渡す。
- 以降のリクエストでは、ブラウザが自動で Cookie を送り、サーバーはそれでログイン中のユーザーを判別する。
- ログアウト時はサーバー側でセッションを破棄する。
- Spring Security の標準的なセッション管理を使用する。
- セッションの有効期限は Spring Boot の初期値（30分間操作がなければ失効）とする。

### 1.3 CSRF対策

- Cookie で認証する方式では、他サイトから勝手にリクエストを送らせる攻撃（CSRF）への対策が必要なため、Spring Security の CSRF 対策を有効にする。
- サーバーは CSRF トークンを Cookie（`XSRF-TOKEN`）で渡し、React は更新系リクエスト（POST / PUT / DELETE）のヘッダー `X-XSRF-TOKEN` にその値を付けて送る。

### 1.4 フロントエンドとバックエンドの配置

- 開発時は React 開発サーバーから `/api` へのリクエストを Spring Boot に転送（プロキシ）する。本番相当の構成では React をビルドした成果物を Spring Boot から配信する。
- どちらの場合もブラウザから見て同じ配信元（オリジン）になるため、CORS 設定は不要とする。

### 1.5 データアクセス制御（FR-027, NFR-003）

- `/api/auth/register` `/api/auth/login` 以外のAPIはログインが必要。未ログインで呼び出した場合は `401` を返す。
- 記録に関するAPIは、ログイン中のユーザー自身の記録のみを対象とする。
- 他ユーザーの記録IDを指定した場合は、存在しない記録と同じく `404` を返す（他ユーザーの記録が存在するかどうかも分からないようにする）。

## 2. 共通仕様

### 2.1 HTTPステータスコード

| コード | 意味 | 主な使用場面 |
|---|---|---|
| 200 OK | 成功 | 取得・更新・ログイン成功 |
| 201 Created | 作成成功 | ユーザー登録・記録作成 |
| 204 No Content | 成功（返す本文なし） | 記録削除・ログアウト |
| 400 Bad Request | 入力内容に誤りがある | バリデーションエラー、検索条件エラー |
| 401 Unauthorized | 未ログイン、またはログイン失敗 | |
| 403 Forbidden | CSRFトークン不正 | |
| 404 Not Found | 対象が存在しない（他ユーザーの記録を含む） | |
| 409 Conflict | 既存データと重複する | メールアドレス重複 |
| 500 Internal Server Error | サーバー内部エラー | |

### 2.2 エラーレスポンス形式

エラー時は以下の形式で返す。

```json
{
  "message": "入力内容に誤りがあります。",
  "errors": [
    { "field": "password", "message": "パスワードは8文字以上で、英字と数字を含めてください。" }
  ]
}
```

| キー | 型 | 説明 |
|---|---|---|
| message | 文字列 | 画面に表示する全体メッセージ |
| errors | 配列 | 項目ごとのエラー。項目に紐付かないエラーの場合は空配列 |
| errors[].field | 文字列 | エラーのある項目名（リクエストのキー名） |
| errors[].message | 文字列 | その項目のエラーメッセージ |

### 2.3 日付・日時の形式

| 種類 | 形式 | 例 |
|---|---|---|
| 日付（対象日） | `YYYY-MM-DD` | `2026-10-10` |
| 日時（作成日時・更新日時） | `YYYY-MM-DDTHH:mm:ss` | `2026-10-10T21:30:00` |

画面での表示形式（[画面レイアウト](../basic-design/screen-layout.md) 1.2節）への変換は React 側で行う。

### 2.4 モードの値

| 値 | 画面表示名 |
|---|---|
| `PROBLEM_SOLVING` | 問題解決 |
| `DIARY` | 日記 |
| `DAILY_REVIEW` | 1日の振り返り |

## 4. 認証API

### API-01 ユーザー登録

`POST /api/auth/register`

リクエスト：

```json
{
  "email": "user@example.com",
  "password": "password123",
  "passwordConfirm": "password123"
}
```

| キー | 型 | 必須 | チェック内容 |
|---|---|---|---|
| email | 文字列 | ○ | メールアドレスの標準形式であること |
| password | 文字列 | ○ | 8文字以上、英字と数字を両方含むこと |
| passwordConfirm | 文字列 | ○ | password と一致すること |

レスポンス：

| ステータス | 場面 | 本文 |
|---|---|---|
| 201 | 登録成功 | なし |
| 400 | 形式不正・入力ルール違反・パスワード不一致 | エラーレスポンス（項目ごとのエラー） |
| 409 | メールアドレス重複 | エラーレスポンス（`field`: `email`） |

- 登録成功時はログイン状態にしない。React はログイン画面へ遷移し、登録完了メッセージを表示する。

### API-02 ログイン

`POST /api/auth/login`

リクエスト：

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

レスポンス：

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | ログイン成功 | `{ "id": 1, "email": "user@example.com" }` |
| 401 | ログイン失敗 | `{ "message": "メールアドレスまたはパスワードが正しくありません。", "errors": [] }` |

- ログイン失敗時は、メールアドレスが存在しない場合もパスワードが誤っている場合も同じレスポンスを返す（NFR-002）。

### API-03 ログアウト

`POST /api/auth/logout`

| ステータス | 場面 | 本文 |
|---|---|---|
| 204 | ログアウト成功 | なし |

- セッションを破棄する。React はログイン画面へ遷移する。

### API-04 ログインユーザー取得

`GET /api/auth/me`

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | ログイン中 | `{ "id": 1, "email": "user@example.com" }` |
| 401 | 未ログイン | エラーレスポンス |

- ブラウザの再読み込みやURL直接入力のあとに、ログイン中かどうかを React が確認するために使う。401 の場合はログイン画面へ遷移する（FR-005）。

## 5. 記録API

### 5.1 記録データの形式

記録の共通項目と、モード別の入力項目（`details`）を入れ子にして返す。

```json
{
  "id": 10,
  "mode": "PROBLEM_SOLVING",
  "title": "仕事の段取りの見直し",
  "targetDate": "2026-10-10",
  "createdAt": "2026-10-10T21:00:00",
  "updatedAt": "2026-10-10T21:30:00",
  "details": {
    "goal": "…",
    "currentState": "…",
    "gap": "…",
    "cause": "…",
    "countermeasure": "…"
  }
}
```

`details` の中身はモードによって異なる（[ER図](../basic-design/er-diagram.md)のモード別テーブルに対応）。

| モード | details のキー |
|---|---|
| PROBLEM_SOLVING | goal, currentState, gap, cause, countermeasure |
| DIARY | memo |
| DAILY_REVIEW | events, reflection, learning, insight, tomorrowTasks |

- タイトル・各入力項目が未入力の場合は `null` を返す。「（無題）」への置き換えは React 側で行う。

一覧系API（API-05, API-06）では、一覧表示に必要な項目のみを返す（`details` は含めない）。

```json
{
  "id": 10,
  "mode": "PROBLEM_SOLVING",
  "title": "仕事の段取りの見直し",
  "targetDate": "2026-10-10",
  "createdAt": "2026-10-10T21:00:00",
  "updatedAt": "2026-10-10T21:30:00"
}
```

### API-05 最近の記録取得

`GET /api/records/recent`

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | 成功 | 一覧用の記録データの配列（更新日時の新しい順、最大5件）。0件の場合は空配列 |

### API-06 記録一覧・検索

`GET /api/records?mode=DIARY&from=2026-10-01&to=2026-10-31&title=仕事`

| パラメータ | 必須 | 内容 | 関連要件 |
|---|---|---|---|
| mode | - | モードの値。省略時は条件に含めない | FR-021 |
| from | - | 対象日の開始日 | FR-022 |
| to | - | 対象日の終了日 | FR-022 |
| title | - | タイトルの部分一致キーワード。省略時・空文字は条件に含めない | FR-024 |

- 指定した条件はすべて AND で結合する（FR-020）。
- 並び順は更新日時の新しい順（FR-018）。

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | 成功 | 一覧用の記録データの配列。0件の場合は空配列（「該当する記録がありません。」の表示は React 側で行う） |
| 400 | `from` と `to` の片方のみ指定 | エラーレスポンス |
| 400 | `from` が `to` より後 | `{ "message": "開始日は終了日以前の日付を指定してください。", "errors": [] }` |

- 日付のチェック（FR-022, FR-023）は React 側でも行い、エラー時は API を呼び出さない。サーバー側でも同じチェックを行う。

### API-07 記録詳細取得

`GET /api/records/{id}`

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | 成功 | 記録データ（`details` を含む） |
| 404 | 記録が存在しない、または他ユーザーの記録 | エラーレスポンス |

### API-08 記録作成

`POST /api/records`

リクエスト（問題解決の例）：

```json
{
  "mode": "PROBLEM_SOLVING",
  "title": "仕事の段取りの見直し",
  "targetDate": "2026-10-10",
  "details": {
    "goal": "…",
    "currentState": "…",
    "gap": "…",
    "cause": "…",
    "countermeasure": "…"
  }
}
```

| キー | 必須 | チェック内容 |
|---|---|---|
| mode | ○ | モードの値のいずれかであること |
| title | - | |
| targetDate | ○ | 日付形式であること。画面では初期値として当日を入れる |
| details | - | mode に対応するキーのみ受け付ける。各項目は任意 |

| ステータス | 場面 | 本文 |
|---|---|---|
| 201 | 作成成功 | 作成した記録データ（`details` を含む）。React はその `id` の詳細画面へ遷移する |
| 400 | 入力内容に誤りがある | エラーレスポンス |

- 作成日時・更新日時はサーバー側で設定する。

### API-09 記録更新

`PUT /api/records/{id}`

リクエスト：API-08 から `mode` を除いたもの。

| ステータス | 場面 | 本文 |
|---|---|---|
| 200 | 更新成功 | 更新後の記録データ（`details` を含む） |
| 400 | 入力内容に誤りがある | エラーレスポンス |
| 404 | 記録が存在しない、または他ユーザーの記録 | エラーレスポンス |

- モードは変更できない（[画面レイアウト](../basic-design/screen-layout.md) 10節 No.1）。リクエストに `mode` が含まれていても無視する。
- 更新日時はサーバー側で設定する。

### API-10 記録削除

`DELETE /api/records/{id}`

| ステータス | 場面 | 本文 |
|---|---|---|
| 204 | 削除成功 | なし |
| 404 | 記録が存在しない、または他ユーザーの記録 | エラーレスポンス |

- 記録と、対応するモード別テーブルの行を物理削除する（[ER図](../basic-design/er-diagram.md) 4節 No.3）。

## 8. 詳細設計で決定した事項

| No. | 項目 | 決定内容 |
|---|---|---|
| 0 | 認証方式 | セッション方式（Cookie）とする |
| 1 | セッションの有効期限 | Spring Boot の初期値（30分間操作がなければ失効） |
| 2 | CSRF対策 | Spring Security の CSRF 対策を有効にし、トークンを Cookie で渡して React がヘッダーに付ける |
| 3 | React と Spring Boot の配置 | 開発時はプロキシで同じ配信元に見せる。本番相当では Spring Boot から React を配信する。CORS 設定は不要 |
| 4 | 他ユーザーの記録へのアクセス | 403 ではなく 404 を返し、記録の存在自体を知られないようにする |
| 5 | エラーレスポンスの形式 | `message`（全体）と `errors`（項目ごと）を持つ JSON |
| 6 | ログインAPIの形式 | Spring Security 標準のフォームログインではなく、JSON を受け取る独自のログインAPIを作る（React から扱いやすいため） |
| 7 | 最近の記録のAPI | 一覧APIとは別に `/api/records/recent` を用意する |
| 8 | 記録データの形式 | 共通項目とモード別項目（`details`）を入れ子にする |
| 9 | 画面のURL | 6節のとおり |
